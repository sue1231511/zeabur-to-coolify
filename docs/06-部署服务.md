# 06 部署服务

每个服务的流程都一样：**新建 → 选仓库 → 选构建方式 → 填端口 → 填域名 → 粘环境变量 → 最后才点 Deploy**。

想偷懒的话，这一步可以交给 AI，见[小妙招：让 AI 替你部署](10-小妙招-让AI替你部署.md)。

## 连 GitHub（只做一次）

地址栏打开 `https://coolify.你的域名.com/sources`，点 **+ Add**，选 **GitHub App**。

- Organization 留空（装在你的个人账号上）
- System wide 不勾
- Pull request previews 用不到可以不勾，权限少要一点
- 下一页点 **Register With GitHub**，跳到 GitHub 创建并选择给它看哪些仓库，回来显示 Connected 就好了
- 注意：GitHub App **看不到你只是协作者的、别人账号下的仓库**。那种仓库如果是公开的，可以按公开仓库部署（推送后要手动点重新部署），或者 fork 一份到自己账号

连好以后，往对应分支推代码会自动触发部署。**推到 main 就等于上线**，改代码前心里有数。

## 新建一个服务

**Projects → 项目 → + New Resource →** 选名字里带 **GitHub App** 的那个 Private Repository。如果你看到一页让你手填 `git@github.com:...` 的地址，就是进错门了，后退重选。

| 选项 | 怎么填 |
|---|---|
| Branch | `main` |
| Build pack | 仓库里有 `Dockerfile` 选 **Dockerfile**；Node / Python 项目没有 Dockerfile 就选 **Railpack**（Node 项目要有 `package.json` 里的 `start` 脚本）。见下面的说明 |
| Base directory | 代码在仓库最外层填 `/`；套了一层文件夹就填那个文件夹，以 `Dockerfile` 所在的位置为准 |
| Port / Ports exposes | **以旧服务实际监听的端口为准。** Zeabur 从源码构建的服务默认是 8080，Coolify 默认填 3000，记得改 |
| Port mappings | 留空，填了会绕过 HTTPS 直接把端口开到公网 |
| Domains | `https://服务名.你的域名.com`，Port 那格也填上端口；不是给人看的接口，搜索引擎收录选不允许 |

**关于构建方式**：有 Dockerfile 就优先用 Dockerfile，行为最可预期。没有 Dockerfile 时，Coolify 4.5.0 里 Nixpacks 已经被标成“已弃用”，所以推荐 Railpack。我们搬家时有几个没 Dockerfile 的服务用的是 Nixpacks，也能正常跑，如果 Railpack 构建不过，可以换 Nixpacks 试试。

**Dockerfile 位置是相对于 Base directory 的**，不要把子目录再写一遍。

## 环境变量（最容易出错）

1. 在 Environment Variables 页切到 **Developer view**，可以整段粘贴。
2. 格式是一行一个 `名字=值`，**值不要加引号**。Coolify 不会去掉引号，会当成值的一部分，导致连不上数据库之类的。
3. 删掉 Zeabur 平台自己加的：`ZEABUR_` 开头的、`CONTAINER_HOSTNAME`、`WEB_PORT`、`PORT_FORWARDED_` 开头的。
4. `PORT` 可以不填，没填时 Coolify 会自动设成第一个暴露的端口。
5. 值里有 `$` 的，要在 Normal view 点开这个变量，把 Interpolation 改成 **Literal**，不然会被当成变量引用改掉。
6. 值里有“空格 + #”的，后面会被当成注释截掉。
7. 保存后切回 Normal view，挑一个不是密钥的变量点开看，确认开头结尾没有多出引号。

**环境变量由你自己粘贴**，别把密钥发给任何人或任何聊天窗口代劳。

指向别的服务的地址（`.zeabur.internal`、`.zeabur.app`、各种 `*_HOST`、`*_URL`），改成新家的域名或下面讲的内网别名。

## 部署

点 **Deploy**，看 **Deployment Logs** 构建过程，右上角变成 Running 就是跑起来了（显示 no healthcheck 不影响）。再看 **Runtime Logs** 有没有报错。浏览器打开域名看到页面或者 `Not Found`，都说明域名、HTTPS、端口这条路是通的（接口服务首页本来就没东西）。

## 只给内网用的服务

有些服务只被你自己的其他服务调用，比如网关背后的各种小工具。它们如果没有鉴权，**不应该出现在公网上**。做法：

1. **删掉自动生成的地址。** Coolify 新建服务时会自动给一个 `http://xxxx.<新IP>.sslip.io` 的公网地址。到 Domains 把它删掉。删除时如果有“顺带删除 DNS 记录”之类的选项，**不要勾**。
2. **不填域名，不填 Port mappings。**
3. **设一个网络别名（Network aliases）**，比如 `svc-weather`。

这样，同一个 Coolify 网络里的其他服务就能用 `http://svc-weather:8080` 访问它，外网访问不到。这就是 `*.zeabur.internal` 的替代品。

建议把这些地址做成环境变量（比如 `WEATHER_URL`），代码里只读变量，以后换地址不用改代码。

## 恢复数据

有数据的服务，先在 **Persistent Storage**（持久存储）→ 添加卷，填容器里的数据目录（比如 `/app/data`），部署一次，让卷建出来。卷的名字在持久存储页能看到（下面写成 `<卷名>`）。

然后把第 03 步的备份放进卷里：

```bash
# 1. 在你电脑上，把备份传到新服务器
ssh root@<新IP> "mkdir -p /root/restore"
scp data.db root@<新IP>:/root/restore/

# 2. 在 Coolify 里先把这个服务停掉，免得拷的时候程序正在写

# 3. 在新服务器上，借一个临时的 alpine 容器把文件拷进卷
docker run --rm -v <卷名>:/data -v /root/restore:/restore alpine cp /restore/data.db /data/data.db

# 4. 核对：结果要和第 03 步备份时算的一模一样
docker run --rm -v <卷名>:/data alpine sha256sum /data/data.db
```

最后在 Coolify 里重新启动服务，打开页面确认数据都在。恢复完删掉新服务器上 `/root/restore/` 里的临时文件，那里面是你的数据。

为什么不用 `docker cp` 拷进容器：在 Coolify 里点“停止”，它会把已退出的容器删掉，到时候找不到容器。直接对卷操作，不管容器在不在都能用。

如果程序要以特定用户读写文件，拷完可能还要调整文件属主，看程序自己的要求。

## 一个一个搬，搬一个验一个

1. 先搬没有数据、没人依赖的小服务，熟悉流程；
2. 再搬被别人依赖的服务；
3. 最后搬有数据的服务，按上面的步骤恢复并核对。
